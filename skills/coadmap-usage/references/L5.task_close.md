### タスクを閉じる前に

タスクの属性（機能・見積り・ラベル・目標）が空いたまま閉じると、「なぜ → 何を → どう作るか」の鎖が切れ、機能ごとの工数やベロシティも数えられなくなる。先行・後続に順序制約があるときは、その依存も次の作業に必要な情報になる。
Yata が出した属性の候補は、タスクに「開いた件」として残っている。**閉じる前に 1 回、まとめて利用者に確かめて確定する。**

作業中に具体的な順序制約を見つけたら、`request_coadmap_task_attribute_suggestions` に `topics: ["dependency"]` と `dependencyCandidate`（相手タスクの ID、対象タスクから見た先行・後続、理由）を渡して候補にする。依存の候補も作業の最後に他の候補と合わせて利用者に確かめる。
別の依存を追加する場合も、相手と向きを指定して変更案にする。タスク取得で読める依存だけを使って依存の一覧を全置換すると、読めない既存の依存を外し得る。画面で直接変更する場合は、事前タスク・後続タスクから個別の依存を操作する。

## 手順

1. **開いた件と空きを読む.** `get_coadmap_task_dependency` の応答の「Open task attribute suggestions」の節、または列を in_review・done へ動かした `update_coadmap_task` の応答の「Before closing: check the task's attributes」の節を見る（どちらも JSON ではなく文の節で返る。件ごとに `decisionRecordId`・`expectedVersion`、候補ごとに `changeSetId` が書かれ、推奨には `(recommended)` が付く。値も候補も無い属性は「Empty attributes with no suggestion」に、Yata がまだ件を作らずに判断している属性は「Attributes Yata is still deciding」に並ぶ。どちらも、その組織で使える属性だけが並ぶ）。
   - 候補が「none yet」の件と、「Attributes Yata is still deciding」の属性（`attributeCheck.pendingTopics`）は、Yata が判断中。確定もせず、利用者に値を聞いて直接書かせもしない。後でタスクを読み直して確かめる（タスクを done へ動かすときにもう一度拾う）。
   - 候補が無く確認の問いがある機能の紐付けの件（「candidates: none. Yata is waiting for the user's answer」と書かれる）は、Yata の判断中ではなく利用者の番。問いを利用者に見せ、機能を選んでもらう（問いに文章で答える口は無い）。選んだ機能は、同意を得てから `update_coadmap_task` で直接紐付ける（利用者が件を確定できる人なら件は閉じる）。合う機能が無ければ、同意を得てから `request_coadmap_task_attribute_suggestions` に `topics: ["pf_link"]`・`rejectCurrentCandidates: true`・`requestNewFeature: true` を渡して、Yata に新しい機能の案を頼む（案は後でタスクを読み直して確かめる）。頼むのは、この件でまだ `requestNewFeature` を頼んでいないときだけ。頼んだ直後は Yata がまだ案を用意している途中のことがある。後で読み直しても（タスクを done へ動かすときに拾い直しても）同じ問いだけの件のままなら、Yata は新しい機能の案を出せなかった。もう一度頼まず、機能を選んでもらう（依頼は「他の候補を出す」と件ごとの回数の枠を共有し、AI クレジットも使う）。
   - 目標は、機能の件が開いているあいだ（機能の判断が決着待ちのあいだ）はどの節にも並ばない。機能が決まると、機能が紐付かなかったタスクでは Yata が目標を判断し始める（機能が紐付いたタスクの目標は機能の側で紐付けるので、目標は並ばない）。機能を確定した直後は目標が「Attributes Yata is still deciding」に並ぶことがある。後でタスクを読み直して確かめる。
   - 「viewerCanConfirm: false」と書かれた件は確定しない（社外の人・判断する人が別の人・タスクを更新できない・件が保留中のどれか）。確定できる人に頼むよう利用者に伝える。保留中の件（属性の件は保留にしないので通常は無く、保留を解く口も無い）は、利用者に値を決めてもらい、同意を得てから属性を直接書く（利用者が件を確定できる人なら、直接書けば件は閉じる。そうでなければ件は開いたまま残る）。
2. **1 回でまとめて聞く.** 件ごとに推奨（`(recommended)` が付いた候補）を並べ、「この内容で確定してよいか」を 1 回だけ利用者に聞く。候補を選んで確定するとタスクが書き換わることも伝える。「後で」（今は決めない）も答えとして受け、その件は確定しない（件の状態の保留 `on_hold` とは別で、件には何もしない）。
   - 作業で分かったこと（変えたファイルが属する機能など）が推奨と食い違うときは、その根拠を添えて別の候補を勧める。
   - どの候補も合わない（候補に無い値を利用者が選んだ）・値も候補も無い属性（「Empty attributes with no suggestion」）は、利用者に値を決めてもらい、示した値への同意を得てから属性を直接書く（`update_coadmap_task`）。利用者が件を確定できる人（タスクを更新できる社内のプロジェクトメンバーで、判断する人がいればその人）なら、直接書けばその属性の開いた件は閉じる（その件の候補でない変更案を利用者が承認して値が入ったときも同じ）。そうでなければ件は開いたまま残るので、確定できる人に伝えるよう利用者に添える。
3. **確定する.** 利用者が了承したら `confirm_coadmap_task_decision` に件の `decisionRecordId`・`expectedVersion`・選んだ `changeSetId`（`selectedChangeSetIds`）を渡す。1 つ以上を選べる件（機能・ラベル・目標）では、利用者が選んだ候補をすべて渡す（ラベル・目標は今の値に足すだけで、今の値は外れない）。「やらない」と言われたら、`selectedChangeSetIds` の代わりに `outcome: not_doing`。「status: confirmed earlier without a selected candidate」の件を「反映しない」で閉じるときは `withoutChange: true`。
4. **版が古い・件が閉じていると言われたら**（409）、タスクを読み直す。利用者が同意した候補（同じ `changeSetId`）が残っていて中身も変わっていなければ、新しい `expectedVersion` で確定し直す。候補が変わっていたら、利用者に確かめ直す。件が消えていれば（誰かが決めたか、閉じて日数がたち取り下げられた）、属性が空いたままなら利用者に値を聞いて直接書く。
5. **done へ動かすときにもう一度聞くのは**、in_review の後に増えた件（候補が「none yet」だった件・Yata が判断中だった属性・機能を確定した後に判断された目標・「合う機能がない」で頼み直した件（同じ `decisionRecordId` でも聞き直す）など）と、利用者が「後で」と答えた件だけ。確定・やらない・直接書く、の答えをもらった件は `decisionRecordId` で突き合わせて聞き直さない。「やらない」で閉じた属性は、閉じた後にその属性の値が変わっていなければ「Empty attributes with no suggestion」にも並ばないので、聞き直さない。

## してはいけないこと

- 利用者に聞かずに確定しない。Yata の候補は判断の材料で、決めるのは人。
- 見積りがすでにあるタスクの見積りを、実績に合わせて書き換えない（ベロシティが計画の精度を表さなくなる）。利用者が明示的に頼んだときだけ書き換える。
- 属性ごとに何度も聞かない。閉じる前の 1 回にまとめる。
