### エピック（`Epic`）

タスクを束ねる大きめの作業単位。プロジェクト（`Workspace`）内に存在する。

## 何か
- 「機能群のリリース」「目標達成に向けたひとまとまりの作業」など、タスクより粒度が大きい作業のまとまり。
- 子に複数のタスクを持つ。
- エピックには対応する Task が 1 つ存在する（`Epic.task`）。タスクとエピックは互いに変換可能（`ConvertTaskToEpic` / `ConvertEpicToTask`）。
  変換しても目標系の紐付けはタスクに残る（ただし、プロジェクトに属さないエピックをタスクに戻すときは紐付けが消える。プロジェクトに属さないタスクは直接の紐付けを持てないため）。タスクをエピックにするときは、変換前の状態で「目標の紐付けを持たないエピック」としての作成権限（プロジェクトの権限）と、紐付いている目標系それぞれの閲覧権限が要る（タスク自身の紐付けからの委譲では通らない。読めない紐付けがあれば変換は理由付きで拒否される）。プロジェクトの紐付けられる範囲の外の目標系への紐付けがあるとき、プロジェクトに属さないタスクに紐付けがあるときも、変換は理由付きで拒否される。エピックに変わると目標による権限の委譲が始まる。エピックをタスクに戻すと委譲が止まるので、戻すにはタスクの更新権限に加えてエピックの更新権限が要る。

## 主な紐付け先

| 相手 | 紐付け方 |
|---|---|
| 機能（`ProductFeature`） | `Epic.productFeatures` の多対多。エピック作成・更新時に `productFeatureIds` で直接紐付け可能 |
| 目標（`Objective`）・イニシアチブ（`Initiative`）・アウトカム（`Outcome`） | 多対多。作成・更新時に `objectiveLinkSubjectIds`（複数可。3 種を混ぜてよく、種類はサーバが判定する）で紐付ける。紐付けはエピックに対応する Task が持ち、タスクと同じ項目・同じ検証（→ [タスク](L1.task.md)）。読み取りは `Epic.objectives` / `Epic.initiatives` / `Epic.outcomes`（閲覧者が読めないもの・紐付けを許可していない種類は出ない）。`initiativeIds` は非推奨（イニシアチブの紐付けとして受け付けるが、`objectiveLinkSubjectIds` と同時には渡せない） |
| タスク（`Task`） | 親子（`Epic.childTasks` / `Task.parentEpics`）。タスク側から `epicIds` で親エピックを指定 |

エピックの紐付けは、エピックでないタスクと違って**権限にも効く**（目標による権限の委譲）。条件は次のとおり。

- 委譲するのは**目標（`Objective`）の紐付けだけ**で、そのうち **ID が最小の目標 1 つ**。イニシアチブ・アウトカムの紐付けは権限に効かない。
- その目標を読める人はエピックを閲覧でき、その目標を更新できる人はエピックを作成・更新・クローズ・再開・移動できる。
- その目標のプロダクトが閲覧者に閉じている（入れない非公開のプロダクト）なら委譲しない（次に小さい ID の目標へは移らない）。
- エピックのプロジェクトが閲覧者に見えなければ、委譲があっても閲覧・編集できない。

**既存のエピックの目標（`Objective`）の紐付けが変わる操作は、どの口からでも、書き込む前の状態のエピックの更新権限が要る**（委譲先が変わるため。これから付ける目標からの委譲では通らない）。
イニシアチブ・アウトカムの紐付けだけが変わる操作には要らない。各口のもともとの権限はそのまま要り、これが足される。

- `update-task` / `update-epic`（変更案の適用・取り消しを含む）: タスク・エピックの更新権限に加えて。担当者はタスクを更新できても、エピックの更新権限が無ければ目標の紐付けは変えられない
- 目標の画面でエピックを追加・外す（`addEpicsToObjective` / `removeEpicsFromObjective`）: 目標の更新権限に加えて、各エピックの更新権限
- ガントでエピックをルートへ出す（`addItemsToWorkspaceGantt` / `flattenWorkspaceGanttItem`。項目がエピックのときだけ、そのエピックとプロジェクトの目標との紐付けが消える。エピックでないタスクの紐付けは消えない）: ガントの更新権限に加えて、そのエピックの更新権限
- エピックをタスクに戻す: タスクの更新権限に加えて、エピックの更新権限

新しくエピックを作るとき（`create-epic`、イニシアチブからのインポート）は、目標の紐付けを持たないエピックとしての作成権限（プロジェクトの権限）と、紐付ける目標系それぞれの閲覧権限が要る。
イニシアチブからのインポートは、作ったエピックにイニシアチブと**その親の目標の両方**を紐付ける（だから委譲が働く）ので、両方の閲覧権限が要る。
ガントで目標の下に並ぶのも、目標の期間を変えたときに期間が連動するのもエピックだけ（エピックでないタスクは並ばず、動かない）。

## タスクとの 2 系統の関係（GraphQL 上）

GraphQL 上、Task↔Epic の関係には 2 系統ある:

- **親子**: タスクが `epicIds` でエピックに属する（`Epic.childTasks` / `Task.parentEpics`）
- **自己対応**: エピックは内部的に対応する Task を 1 つ持つ（`Epic.task` / `Task.epic` when `Task.isEpic` is true）

## 作成・更新時に指定できるフィールド

- **作成時必須**: `title` / `namespace` / `workspaceId`
- **作成時のみ指定可**: `pipelineId`（`UpdateEpicRequest` には無い）。
  ただし列を動かせないわけではなく、エピックは対応する Task を持つため
  `PATCH /tasks/{id}` の `pipelineId`（`UpdateTaskRequest`）で移動する
- **作成・更新の両方**: `description` / `isHighPriority` / `estimateValue` / `assigneeIds` /
  `labelIds` / `sprintIds` / `releaseIds` / `epicIds` / `productFeatureIds` /
  `objectiveLinkSubjectIds` / `knowledgeIds` / `roadmapIds` / `connectedCraftIds` / `craftDiffScopeIds`
- **更新でのみ指定できる**: `since` / `until`
- `workspaceId` は作成時だけ指定する（`UpdateEpicRequest` には無い）。**Yata の経路からはエピックを別プロジェクトへ移せない**。
  移動は画面の「他のプロジェクトに移す」（GraphQL の `transferTask` に、エピックに対応する Task の ID を渡す）で行う。
  移るのはエピック自身だけで、子タスクは元のプロジェクトに残る（親子の紐付けは残る）。番号は移動先で振り直される。
  スプリント・親エピック・機能・リリース・依存・PR の紐付けは外れ、移動元のガントからも外れる（移動先のガントには載らない）。
  担当者は移動先のメンバーである人だけ、見積もりは移動先にある値だけ、ラベルは同名のものだけ残る。列は移動先の既定の列になる。

タスクとの違い: **エピックは `knowledgeIds` と `roadmapIds` を指定できるが、タスクは指定できない**
（`CreateTaskRequest` に無い → [タスク](L1.task.md)）。
逆に**タスク依存（`predecessorTaskIds` / `successorTaskIds`）はタスクの更新でしか張れない**。

## エピックを生成する経路

- 通常の作成（タイトル・機能・イニシアチブ等を直接指定して作る）
- イニシアチブ（`Initiative`）からのインポート（`ImportInitiativesAsEpicsInput`）— オブジェクティブヒエラルキー上のイニシアチブを複数選択して、プロジェクトのエピックとして一括生成
