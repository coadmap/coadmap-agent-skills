# Coadmap の使い方

> この Skill は Coadmap の使い方の説明書から自動で作られている。手で直さない。

## 思想（なぜそうするか）

### 「なぜ・何・どのように」を切らさない

Coadmap の根幹は **「なぜ／なんのために／何を／どのように作るのか」を常に意識する**こと。
作業（タスク）だけが宙に浮いて、何のための作業か辿れない状態を作らない。

## 鎖

- **目標・顧客価値（なぜ）↔ 機能（何を）** の紐付け
  - プロダクトヒエラルキーの「目標カラム」または機能詳細サイドバー「目標・顧客価値」で紐付ける
- **機能（何を）↔ タスク／エピック（どのように）** の紐付け
  - タスク・エピック作成・更新時に `productFeatureIds` で紐付ける
- **目標・イニシアチブ・アウトカム（なぜ）↔ タスク／エピック（どのように）** の直接の紐付け
  - タスク・エピック作成・更新時に `objectiveLinkSubjectIds` で紐付ける
- **イニシアチブ → エピック**
  - イニシアチブ（`Initiative`）からプロジェクトに**エピックとしてインポート**することで繋ぎを作れる

## 作業を作るときは機能への接続を確保する

- タスク・エピックを作るときは関連する**機能**を紐付ける。
- 機能につながっていれば、その先の目標まで鎖が通る。
- 機能につながらない孤立した作業は鎖が切れる。
- 機能では「なぜ」を言い表せない作業（調査・運用・改善の単発タスクなど）は、目標・イニシアチブ・アウトカムへ直接紐付けて鎖を保つ（`objectiveLinkSubjectIds`）。

## 調査が先、断定は後

鎖を正しく扱うには、まず**実在する機能・目標を調べる**必要がある。
プロダクトヒエラルキー／オブジェクティブヒエラルキーを取得してから判断し、推測で断定しない。

## 構造（どう繋がるか）

### 主な繋がり方

Coadmap は **2 つの独立したヒエラルキー** ＋ **プロジェクトの実行レイヤー** で構成される。

## 2 つのヒエラルキー（独立）

- **プロダクトヒエラルキー**（What）: プロダクト → コンポーネント → 機能 → サブ機能
- **オブジェクティブヒエラルキー**（Why）: 目標 → （サブ目標 / イニシアチブ / アウトカム）

## 主な紐付け方の一覧

| 繋ぎ | 経路 |
|---|---|
| 目標 ↔ 機能 | (1) プロダクトヒエラルキーの「目標カラム」 (2) 機能の詳細サイドバー「目標・顧客価値」 |
| 機能 ↔ タスク | タスク作成・更新時の `productFeatureIds`（多対多） |
| 目標・イニシアチブ・アウトカム ↔ タスク・エピック | タスク・エピックの作成・更新時の `objectiveLinkSubjectIds`（多対多。種類はサーバが判定する） |
| 機能 ↔ エピック | エピック作成・更新時の `productFeatureIds`（多対多） |
| イニシアチブ → エピック | `ImportInitiativesAsEpicsInput` でイニシアチブをプロジェクトのエピックとして一括生成 |
| エピック ↔ タスク | `epicIds` で親子（`Epic.childTasks` / `Task.parentEpics`）、および自己対応（`Epic.task` / `Task.epic`） |
| リリース ↔ 機能 | (1) プロダクトヒエラルキーの「リリースカラム」 (2) `AddProductFeaturesToReleasesInput`（多対多、任意の `state` 付き）。**Yata の経路からは張れない** |
| リリース ↔ タスク・エピック | タスク・エピックの作成・更新時の `releaseIds`（どちらも Yata の経路から指定可）、または `AddTasksToReleasesInput`（多対多。エピックは対応する Task で紐付く） |
| リリース ↔ 目標・アウトカム・イニシアチブ | (1) オブジェクティブヒエラルキーの「リリースカラム」 (2) `AddObjectiveHierarchyNodesToReleasesInput`（多対多。種別を混在して一度に紐付け可）。**Yata の経路からは張れない** |

## 縦と横の役割

| 縦（木） | 横（紐付け） |
|---|---|
| プロダクトヒエラルキー、オブジェクティブヒエラルキー | 目標 ↔ 機能、機能 ↔ タスク、機能 ↔ エピック、目標ツリー ↔ タスク・エピック、リリース ↔ 機能・タスク・目標ツリー |
| 親子・分類 | 別カテゴリ間の関連 |

役割が違うので統合して考えない。

## 廃止

機能の `ancestor` / `descendant`（バージョン履歴）は廃止（ノートのバージョン機能で置換済み）。
共通化の `master` / `references`（同一機能の使い回し）とは別物なので混同しない。

### 関係の種類

「誰が・何が・どう繋がっているか」を答えるときは、**関係の種類を区別する**。種類が違えば根拠も違い、言い換えは誤りになる。

## 種類と根拠

| 種類 | 意味 | 根拠 |
|---|---|---|
| **所属** | 人がプロジェクトのメンバーである | `WorkspaceMembership`（プロジェクト設定のメンバー一覧） |
| **閲覧できる** | 見えるが、メンバーではない | 公開プロジェクトなど。可視性の結果であって所属ではない |
| **担当** | 人がタスク・エピックのアサイニーである | `Task.assignees` |
| **親子** | 木の上下関係 | プロダクトヒエラルキー / オブジェクティブヒエラルキーの親子、`Epic.childTasks` / `Task.parentEpics` |
| **参照** | 別カテゴリ間の紐付け | 機能 ↔ タスク・エピック（`productFeatureIds`）、目標 ↔ 機能、目標・イニシアチブ・アウトカム ↔ タスク・エピック（`objectiveLinkSubjectIds`） |
| **依存** | 作業の前後関係 | `Task.predecessorTasks` / `Task.successorTasks` |

## 混同しやすい組み合わせ

**所属 ≠ 閲覧できる**

プロジェクト一覧を返す手段は、既定では「呼び出した人が**閲覧できる**プロジェクト」を返す。ここには本人がメンバーでない公開プロジェクトが含まれる。所属を答えるには、関係が **所属** と明示されている行だけを根拠にする。

**所属 ≠ 担当**

タスクの担当者であることは、そのプロジェクトのメンバーであることを意味しない。逆も同じ。

**階層種別を言い換えない**

プロダクトヒエラルキーの各ノードは種別を持つ（プロダクト / コンポーネント / 機能）。機能をコンポーネントと呼び替えると階層が 1 段ずれる。種別はツールの応答に含まれるので、そこに書かれている種別をそのまま使う。

## 可視範囲という制約

どの一覧も、呼び出した人が見える範囲に限られる。したがって**「全部で N 件です」と断定できるとは限らない**。数を答えるときは、見える範囲での件数であることを明示する。

所属の一覧から外れるものは 3 つある。

| 外れるもの | 理由 |
|---|---|
| 連携していない他組織のプロジェクト | 自組織と、自組織へ連携された他組織のプロジェクトだけを扱う |
| 呼び出した人に見えないプロジェクト | 非公開で本人がメンバーでないもの |
| アーカイブ済みのプロジェクト | 一覧は進行中のものだけを扱う |

人は複数の組織に所属していることがある。**今いる組織から見える範囲での所属**を答えているのであって、その人の所属のすべてではない。

## 規約（運用の正解）

### ユーザーには画面の呼び名で話す

**ユーザーに向けて話すときは、GraphQL の型名・API のフィールド名ではなく、
Coadmap の画面に出ている日本語の呼び名を使う。**

ユーザーは画面の言葉で Coadmap を覚えている。型名で返すと、ユーザーは自分が見ている画面の
どこの話なのか分からない。型名は、こちらが内部で対象を特定するための識別子でしかない。

- ○「このプロジェクトのリスク台帳に載せますか？」
- ×「この Workspace の RiskRegisterItem を作成しますか？」
- ○「機能紐付け提案が出ています」
- ×「TaskProductFeatureLinkProposal が pending です」

型名を出してよいのは、ユーザーが API・スキーマの話をしているときだけ。

## 迷ったとき

画面の呼び名が分からないときは、型名をそのままカタカナにせず、
**その画面でユーザーが何をする場所かを言葉で説明する**。
存在しない機能名を作らない。

## 作法（やること）

### 関係を聞かれたときの答え方

## 状況
「この人はどのプロジェクトに所属しているか」「この機能に関係するタスクは何か」「これに関係するものを関係の種類ごとに洗い出して」のように、**リソース同士の繋がり**を聞かれた。

## 振る舞い

1. **関係の種類を明示して答える**。「所属」「閲覧できる」「担当」「親子」「参照」「依存」のどれなのかを、項目ごとに書く。種類を書けないものは関係として挙げない。
2. **所属を答えるときは、関係が所属だと示されている行だけを使う**。閲覧できるだけのプロジェクトを所属として挙げない。閲覧できることに触れる場合は「閲覧できる」と書く。
3. **タイトルの一致は関係の根拠にしない**。機能に関連するタスクは、タスク検索の機能絞り込み（実際の紐付けだけが返る）で列挙する。紐付けが確認できないものを挙げる場合は「紐付けは確認できていない候補」と明示する。
4. **件数を断定しない**。一覧は見える範囲に限られるため、「見えている範囲では N 件」と書く。全数を保証できるかどうか分からないときは、そう書く。
5. **階層種別はツールの応答に書かれているものをそのまま使う**。機能をコンポーネントと呼び替えない。
6. 関係を取得する手段が無い、または取得できなかったときは、**推測で埋めずに「確認が必要」と伝える**。

## 答え方の形

種類ごとに分けて並べる。混ぜない。

```
所属しているプロジェクト（閲覧できる範囲で 3 件）
- [プロジェクトA](<URL>)
- ...

閲覧できるが所属していないプロジェクト（2 件）
- ...

紐付けは確認できていない候補
- タイトルに同じ語を含むだけのため、関係は未確認
```

## なぜ

「見えている」と「入っている」を言い換えると、人と組織の状態を誤って伝えることになる。名前が似ているだけのものを関係ありと断定すると、ユーザーは実在しない繋がりを前提に判断してしまう。関係の種類が書けないものは、そもそも関係が確認できていない。

### 読んだ資料をもとに書く

## 状況
道具や調査で読んだ Coadmap の資料（タスク・機能・会議・リスク台帳など）をもとに、報告や回答を書く。

## 振る舞い

1. 資料から書いたことには、**その資料へのリンクを添える**。リンクは道具や調査が返した URL を**そのまま**使い、自分で組み立てない。
2. 会議の記録やリスクのように 1 件ずつの画面が無い資料は、道具が返す画面（会議の記録はその会議の記録のページ、リスクはリスク台帳タブ）へリンクする。
3. 状態や種類は**日本語の呼び方**で書く。道具や API に出てくる英語の内部の値（`ACCEPTED` など）は本文に書かない。
4. 資料で確かめられなかったことは、確かめられなかったと書く。読んでいない資料を読んだように書かない。

## なぜ

リンクが無いと、読み手は書いてあることの出どころを確かめられない。組み立てた URL は崩れて開けないことが多い。英語の内部の値は読み手にとって意味が通じない。

### 答える前に調査する

## 状況
ユーザーが機能・目標・つながりについて質問してきた、または提案を求めてきた。

## 振る舞い

1. **先にプロダクトヒエラルキー／オブジェクティブヒエラルキーを取得**する。
2. 取得した**実在のリソースに基づいて**答える。記憶や一般論で即答しない。
3. リソースには**タイトル**で言及する。**生の ID を表に出さない**。
4. プロジェクト固有のルール・運用慣習が関係する場合はプロジェクトの `primaryAiContextNote` も参照する。
5. 調べる手段が無い／確証が無いときは、断定せず「確認が必要」である旨を伝える。

## なぜ

推測で断定すると鎖の繋ぎが嘘になる。実在しない機能名で答えるとユーザーが混乱する。

### タスク・エピックを作るとき

タスクやエピックを作るシーンでの作法を 1 つにまとめる。
書き込みは副作用なので、確認 → 必要な紐付け確保 → 作成 の順で進める。

## まず確認する

### 読み取り意図でないか
「教えて」「どれが優先？」「これは何？」のような**情報を聞かれているだけ**のときは、
タスク・エピックを**作らない**。調べて答えるだけにとどめる（→ 質問対応）。

### プロジェクト固有のルールがあるか
プロジェクトの `primaryAiContextNote`（AI 用コンテキストノート）にプロジェクト固有のルール・運用慣習・命名規則などが書かれていることがある。タスクを作る前にこれを参照する。

### 起票するか・どの粒度かを見極める

**鉄則: 機能まるごと・曖昧で大きい依頼を、`create_coadmap_task` 1 件だけで終わらせない。**
「在庫管理を一から作りたい」「決済機能を作りたい」のような**1 つの機能まるごと**の依頼に対して、
タスクを 1 件だけ作って完結する（＝丸ごと 1 タスク）のは**禁止**。必ず下の手順で粒度を決める。

依頼の種類を 5 つに分けて、対応を変える。

1. **読み取り意図だけ**（「教えて」「どれが優先？」）→ **作らない**。調べて答える。
2. **機能まるごと・大きいスコープ**（「在庫管理を一から作りたい」「〜機能を作りたい」など、複数の作業に明らかに割れる）
   → **エピックを 1 つ作る**（`create_coadmap_epic`）。配下タスクは併せて数件作ってもよい。
   **タスク 1 件で済ませない。タスクで平置きしない。**
3. **中くらい（2〜数件に割れる）**（1 つの画面・1 本の API 改修など、関連する複数の作業に分かれる）
   → **数件（目安 4 件以内）のタスク**に分ける。無理にエピックにしない・1 件に丸めない。
4. **小さく明確な単一作業**（「プロフィール画面に電話番号フィールドを追加する」など、
   1 つの作業として完結する）→ **その場でタスクを 1 件だけ作る**。確認で止めない・無理に刻まない。
5. **何を・どの粒度で起票すべきか読み取れない**（「全部やっておいて」「いい感じに」）
   → いきなり create を連打しない。先に **(a) 分解案（粒度と件数）を提示して合意** か
   **(b) 足りない点を確認** してから作る。

**確信が持てないときは、1 件に丸めるのではなく「エピック化」か「確認」を選ぶ。**
**明示的に起票を依頼されていて機能まるごとなら、確認に倒さず迷わずエピック化を選ぶ。**
少なすぎる丸ごと 1 も、多すぎる量産も避け、スコープに見合った構造にする。

## 必須フィールド

タスク・エピック作成時の必須は 3 つ:

- **`title`**: タイトル
- **`namespace`**: 所属ネームスペース
- **`workspaceId`**: 配置するプロジェクト

**`pipelineId` は必須ではない**。省略するとプロジェクトのデフォルト pipeline に入る。

## 機能（`ProductFeature`）の紐付け

タスク・エピックには関連する**機能を紐付ける**（`productFeatureIds`）。鎖（目標 → 機能 → 作業）を切らさないため。

1. **関連しそうな機能をプロダクトヒエラルキーから探す**。
2. 妥当な機能があれば、`productFeatureIds` に紐付ける。
3. **該当する機能が無ければ、無関係な機能を無理に付けない**。ユーザーに確認するか、新しい機能の作成を提案する。
   作業の「なぜ」が機能では言い表せない（調査・運用・改善の単発の作業など）ときは、適切な目標・イニシアチブ・アウトカムが
   既にあれば、それに `objectiveLinkSubjectIds` で直接紐付けることも選べる（→ [タスク](references/L1.task.md)）。
   紐付け先は推測で選ばず、オブジェクティブヒエラルキーで実在を確かめ、作業との関係が明らかなものだけにする。

## エピック配下のタスクは親エピックの機能を継承する

ある親エピックの配下にタスクを作るときは:

1. `epicIds` に**親エピックを設定**する。渡すのは **Epic-id**（`get_coadmap_workspace_context` の `epics[].id`）であり、mention や会話で得た **Task-id をそのまま渡さない**（エピックは対応する Task を別 ID で持つ → [エピック](references/L1.epic.md)）。
2. **親エピックに紐づいている機能を、新しいタスクにも紐付ける**（`Epic.productFeatures` から引いて `productFeatureIds` に乗せる）。

機能 ↔ タスクの紐付けと、機能 ↔ エピックの紐付けはそれぞれ独立した多対多の紐付け。
親エピックの機能がタスクに自動継承されるわけではないので、Yata が明示的に紐付ける。

## その他の主な紐付け

タスク作成時に他にも考慮できるフィールド:

| フィールド | いつ指定するか |
|---|---|
| `description` | 背景・受け入れ条件など本文を書くとき（Markdown） |
| `assigneeIds` | 担当者が明らかなとき。複数可 |
| `labelIds` | プロジェクト固有のラベル規約があるとき（`primaryAiContextNote` 参照） |
| `estimateValue` | ストーリーポイントの推定値。プロジェクト規約があれば従う |
| `sprintIds` | 直近のスプリントに入れるべきとき |
| `releaseIds` | 特定リリースに紐づく作業のとき |
| `isHighPriority` | 優先度が高いと明示されたとき |
| `since` / `until` | ユーザーが日付を明示したときだけ。**ガントチャートに載る**ため推測で埋めない |

**タスクでは指定できないもの**: `assignAiAgents` / `knowledgeIds` / `roadmapIds` は
`CreateTaskRequest` に無い。エピックの作成では `knowledgeIds` / `roadmapIds` を指定できる
（→ [エピック](references/L1.epic.md)）。

`since` / `until` を入れると、そのタスク・エピックはガントチャート上に期間として現れる
（ガントチャートに載るのはエピック・目標・タスク）。
日付を置くこと自体が計画の表明になるので、**ユーザーが言っていない日付を埋めない**。
「いつまでですか」と聞くか、空のままにする。

**タスク依存は作成時に張れない**。`predecessorTaskIds` / `successorTaskIds` は
更新（`UpdateTaskRequest`）でのみ指定でき、いずれも**全置換**（渡した配列で置き換わる。追加ではない）。
事前タスク・後続タスクを張りたい場合は、作成したあとに更新で張る。

## エピックを作るとき

エピック固有のフィールド:

- `productFeatureIds`: 紐づける機能（複数可）。直接紐付け可能。
- `objectiveLinkSubjectIds`: 紐づける目標・イニシアチブ・アウトカム（**複数可**）。タスクでも同じ項目で指定できる。
  エピックでは、紐付けた目標のうち ID が最小のものを読める人・更新できる人が、そのエピックを閲覧・編集できるようになる
  （イニシアチブ・アウトカムの紐付けと、エピックでないタスクの紐付けは権限を変えない。委譲の条件 → [エピック](references/L1.epic.md)）。
  作るときは、目標の紐付けを持たないエピックとしての作成権限（プロジェクトの権限）と、紐付ける目標系それぞれの閲覧権限で判定する
  （これから付ける目標からの委譲では通らない）。既存のエピックの目標の紐付けを後から変えるには、変える前の状態のエピックの更新権限が要る
  （イニシアチブ・アウトカムだけなら要らない）。
- `knowledgeIds` / `roadmapIds`: エピックでのみ指定できる。

イニシアチブ（`Initiative`）からエピックを生成したい場合は、`ImportInitiativesAsEpicsInput`
（複数のイニシアチブを一括でエピック化）も使える。作ったエピックには、イニシアチブとその親の目標の両方が紐付く。

## パイプラインの選び方

タスクを作るときの `pipelineId` は通常プロジェクトのデフォルト pipeline で良い。
特定のステータスに置きたい場合は、**まず `role` を確認**し、無ければ名前で類推する（→ パイプラインの `role`）。

`role = DONE` の pipeline に動かすとタスクは自動で close される（`closed_at` / `actual_finished_at` 自動入力）ので、close する意図がないなら DONE に動かさない。
